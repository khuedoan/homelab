Khue's Homelab

Khue’s Homelab

Features • Get Started • Documentation

This project utilizes Infrastructure as Code and GitOps to automate provisioning, operating, and updating self-hosted services in my homelab. It can be used as a highly customizable framework to build your own homelab.

What is a homelab?

A homelab is a laboratory at home where you can self-host, experiment with new technologies, practice for certifications, and so on. For more information, please see the r/homelab introduction and the Home Operations Discord community (formerly known as k8s-at-home).

If you encounter an issue, please create a bug report (avoid asking for support about issues specific to this project in other communication channels).

Hardware requirements

Initial controller

Note

The initial controller is the machine used to bootstrap the cluster, we only need it once, you can use your laptop or desktop

  • A Linux machine with Nix and sudo access (for privileged ports when PXE booting with Nixie).
  • An SSH agent, preferably with a TPM-backed key to keep the private key in hardware.
  • Add your public SSH key to infra/src/modules/metal/flake/authorized_keys.

Servers

Any modern x86_64 computer(s) should work, you can use old PCs, laptops or servers.

Note

This is the requirements for each node

ComponentMinimumRecommended
CPU2 cores4 cores
RAM8 GB16 GB
Hard drive128 GB512 GB (depending on your storage usage, the base installation will not use more than 128GB)
Node count1 (check out the single node cluster adjustments tutorial)3 or more for high availability

Additional capabilities:

  • Ability to boot from the network (PXE boot)
  • Wake-on-LAN capability, used to wake the machines up automatically without physically touching the power button

Network setup

  • All servers must be connected to the same wired network with the initial controller
  • Access to your domain’s DNS settings in Cloudflare

External resources

A domain managed by Cloudflare is required.

Although I try to keep the amount of external resources to the minimum, there’s still need for a few of them. Below is a list of external resources and why we need them (also see some alternatives below).

ProviderResourcePurpose
CloudflareR2 bucketOpenTofu state
CloudflareDNSDNS and DNS-01 challenge for certificates
CloudflareTunnelPublic services to the internet without port forwarding
BackblazeB2 bucketEncrypted volume backups
ntfy.shUpstreamPush relay for self-hosted ntfy notifications

To avoid vendor lock-in, each external provider must have an equivalent alternative that is easy to replace:

  • Cloudflare R2 and Backblaze B2: any other S3-compatible object storage.
  • Cloudflare Tunnel: access everything via VPN, or use port forwarding, or a small VPS with WireGuard to route traffic (see also awesome tunneling).

Create credentials

You’ll need a password manager to store credentials. I’m using pass, but you can use any password manager with a CLI.

Example infra/${ENV}/.envrc change for another password manager (in this case Bitwarden):

-CLOUDFLARE_API_TOKEN="$(pass "homelab/production/cloudflare/token")"
+CLOUDFLARE_API_TOKEN="$(bw get password "homelab/production/cloudflare/token")"

Tip

Prefer offline-first password managers such as pass or KeePassXC so infrastructure bootstrap doesn’t depend on an external online service.

Cloudflare

  1. Add your domain to Cloudflare and enable R2.
  2. Create a token under Manage Account -> Account API Tokens -> Create Token -> Start from scratch:

Entire AccountAccount API TokensEdit
Entire AccountWorkers R2 StorageEdit

Then store the credentials in your password manager, e.g.:

pass insert homelab/production/cloudflare/account-id
pass insert homelab/production/cloudflare/token-id
pass insert homelab/production/cloudflare/token

Backblaze

Generate a new B2 master application key and store the credentials in your password manager, e.g.:

pass insert homelab/production/backblaze/key-id
pass insert homelab/production/backblaze/key

Important

Each B2 account has one master application key, so you likely need to use the same key for both staging and production.

BIOS setup

Note

You need to do it once per machine if the default config is not sufficient, usually for consumer hardware this can not be automated (it requires something like IPMI to automate).

Common settings:

  • Enable Wake-on-LAN (WoL) and network boot
  • Use UEFI mode and disable CSM (legacy) mode
  • Disable secure boot

Boot order options (select one, each has their pros and cons):

  1. Only boot from the network if no operating system found: works on most hardware but you need to manually wipe your hard drive or delete the existing boot record for the current OS
  2. Prefer booting from the network if turned on via WoL: more convenience but your BIOS must support it, and you must test it thoroughly to ensure you don’t accidentally wipe your servers

Note

Example

Below is my BIOS setup for reference. Your motherboard may have a different name for the options, so you’ll need to adapt it to your hardware.

Devices:
  NetworkSetup:
    PXEIPv4: true
    PXEIPv6: false
Advanced:
  CPUSetup:
    VT-d: true
Power:
  AutomaticPowerOn:
    WoL: Automatic  # Use network boot if Wake-on-LAN
Security:
  SecureBoot: false
Startup:
  CSM: false

Gather information

  • MAC address for each machine
  • OS disk name (for example /dev/sda)
  • Choose a static IP address for each machine (just the desired address, we don’t set anything up yet)
  • Choose an unused IP range for LoadBalancer Services (e.g. 192.168.1.224/27) and a control-plane VIP (e.g. 192.168.1.100)
  • Subnet prefix length and gateway

VPN setup

You can choose between Tailscale, WireGuard, or use both like me. I primarily use WireGuard but keep Tailscale as a backup for when the WireGuard server is down.

Tailscale (requires third-party account)

Tailscale provides access through a subnet router in the cluster.

  1. Select the environment’s kubeconfig:

    export KUBECONFIG="$PWD/infra/production/kubeconfig.yaml"

  2. Read the router’s login URL:

    kubectl -n tailscale logs deployment/tailscale

  3. Open the login URL and enroll the device in your tailnet.

  4. Approve its advertised subnet in the Tailscale admin console.

  5. Install Tailscale on your devices, sign in, and enable subnet routes where required by the client.

You can invite users to your tailnet.

WireGuard (requires port-forwarding)

WireGuard Portal is available at https://vpn.<domain> with SSO.

Prerequisites

Configure port forwarding in your router for the WireGuard service.

Note

Example

Each router is different, here’s mine for reference:

  • Protocol: UDP
  • Start Port: 51820
  • End Port: 51820
  • Local IP Address: 192.168.1.226 (find it with kubectl get service -n wireguard wireguard-wireguard)
  • Start Port Local: 51820
  • End Port Local: 51820

Configure the server

Sign in to the portal with an account in the admins group and create a server interface:

  • Name: wg0
  • Address: 10.44.0.1/24
  • Listen port: 51820
  • Enable default peer creation
  • Client network: 10.44.0.0/24
  • Client endpoint: wg.<domain>:51820
  • Client allowed IPs: 10.44.0.0/24 and your application LoadBalancer subnet

Choose a tunnel network that doesn’t overlap your LAN, pod, or Service networks.

Add a new device

WireGuard Portal will create one device by default. Users can add more if needed.

Install WireGuard, then download the configuration as wg0.conf or scan its QR code. Keep the configuration private.

Mobile

Scan the QR code from the portal using the official WireGuard app.

Linux

Import the WireGuard configuration using NetworkManager:

nmcli connection import type wireguard file wg0.conf

Activate the connection:

nmcli connection up wg0

Connect and test access to a private application while outside your LAN.

Secrets management

Overview

  • Secrets are stored in OpenBao.
  • Integrate with GitOps using the Bank-Vaults secrets webhook.
  • Secrets that can be generated are automatically generated and stored in OpenBao.
flowchart TD
  operator[Bank-Vaults operator] -- generate --> OpenBao
  setup[Just recipes] -- sync infrastructure secrets --> OpenBao
  webhook[Secrets webhook] -- read --> OpenBao

  subgraph app-namespace[application namespace]
    Secret --> App
  end

  webhook -- inject --> Secret

Generated and external secrets

  • Bank-Vaults generates secrets configured in infra/src/modules/platform/openbao.tf, keeping existing values.
  • just deploy syncs infrastructure credentials from OpenTofu’s secrets outputs, along with SSO and Forgejo credentials.

Infra secret outputs

To publish secrets from an OpenTofu module, add a sensitive secrets output.

output "secrets" {
  sensitive = true
  value = {
    "cert-manager/cloudflare" = { # OpenBao path
      api_token = cloudflare_account_token.cert_manager.value # secret values
    }
  }
}

just deploy production writes these under OpenBao’s secret KV mount.

Secret injection

Secrets use <namespace>/<name> paths, for example forgejo/admin. Applications can only read secrets for their own namespace.

When you apply a Secret containing a reference, for example:

apiVersion: v1
kind: Secret
metadata:
  name: forgejo-admin
  namespace: forgejo
stringData:
  username: forgejo_admin
  password: bao:secret/data/forgejo/admin#password

The webhook reads the password from OpenBao and stores it in the Kubernetes Secret.

References are resolved when the Secret is created or updated. After rotation, reapply the references and restart the applications using the Secret.

Please see the official documentation for more information.

Certificate management

Certificates are generated and managed by cert-manager with Let’s Encrypt, and renewed automatically.

cert-manager watches Gateway resources across the cluster. When you create a Gateway with the issuer annotation:

apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  annotations:
    cert-manager.io/cluster-issuer: acme
  name: gateway
  namespace: istio-system
spec:
  gatewayClassName: istio
  listeners:
    - name: https
      hostname: '*.example.com'
      port: 443
      protocol: HTTPS
      tls:
        mode: Terminate
        certificateRefs:
          - name: wildcard-tls
      allowedRoutes:
        namespaces:
          from: All

flowchart LR
  User -- 6 --> Gateway

  subgraph cluster[Homelab cluster]
    Gateway --- Secret
    Gateway -. 1 .-> Certificate
    Certificate -. 5 .-> Secret
    Certificate -- 2 --> CertificateRequest -- 3 --> Order -- 4 --> Challenge
  end

  Order -.- ACMEServer[ACME server]

  subgraph dnsprovider[DNS provider]
    TXT
  end

  Challenge -- 4.a --> TXT
  ACMEServer -.- Challenge
  ACMEServer -. "4.b" .-> TXT
  1. cert-manager creates a corresponding Certificate resource
  2. Based on the Certificate resource, cert-manager creates a CertificateRequest resource to request a signed certificate from the configured ClusterIssuer
  3. The CertificateRequest will create an order with an ACME server (we use Let’s Encrypt), which is represented by the Order resource
  4. Then cert-manager will perform a DNS-01 Challenge:
    1. Create a DNS TXT record (contains a computed key)
    2. The ACME server retrieve this key via a DNS lookup and validate that we own the domain for the requested certificate
  5. cert-manager stores the certificate (typically tls.crt and tls.key) in the Secret specified in the Gateway configuration
  6. Now you can access the HTTPS website with a valid certificate

A much more detailed diagram can be found in the official documentation under certificate lifecycle.

Expose services to the internet

Note

This tutorial is for Cloudflare Tunnel users, please skip if you use port forwarding.

Apply the environment’s tunnel unit to create a tunnel if you haven’t already, then attach your HTTPRoute to the public Gateway (replace example.com with your domain):

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: website
  namespace: website
  annotations:
    external-dns.kubernetes.io/cloudflare-proxied: "true"
spec:
  parentRefs:
    - name: public
      namespace: istio-system
      sectionName: https
  hostnames:
    - www.example.com
  rules:
    - backendRefs:
        - name: website
          port: 3000

The public Gateway supplies the DNS target for the environment’s tunnel.

Backup and restore

Prerequisites

From the development shell, select the environment and its kubeconfig:

env=production
export KUBECONFIG="$PWD/infra/$env/kubeconfig.yaml"

Back up the cluster

Velero runs hourly backups. To create one now:

velero backup create --from-schedule cluster --wait
velero backup get
velero backup describe BACKUP_NAME --details

Check the result for warnings and failed uploads.

Restore an application

Pause the affected Argo CD Applications and their ApplicationSet, then stop the workloads.

Start in read-only mode:

export TF_VAR_backup_read_only=true
(cd "infra/$env/platform" && terragrunt run apply)

Check that app reconciliation remains paused after applying the platform.

Select a backup and restore the app namespace:

velero backup get
velero restore create --from-backup BACKUP_NAME --include-namespaces APP_NAMESPACE --wait
velero restore get
velero restore describe RESTORE_NAME --details

Verify the restored data before resuming workloads and GitOps reconciliation. Then resume scheduled backups:

unset TF_VAR_backup_read_only
(cd "infra/$env/platform" && terragrunt run apply)

Nodes not booting from the network

  • Plug a monitor and a keyboard to one of the bare metal node if possible to make the debugging process easier
  • Check if the controller (PXE server) is on the same subnet with bare metal nodes (sometimes Wifi will not work or conflict with wired Ethernet, try to turn it off)
  • Check if bare metal nodes are configured to boot from the network
  • Check if Wake-on-LAN is enabled
  • Check the controller’s firewall config to make sure that the following ports are open:
    • UDP 67 and 68 for DHCP
    • UDP 69 for TFTP
    • UDP 4011 for the PXE boot service
    • TCP 80 for the boot files
    • TCP 5000 for the installer callback API
  • Check if the servers are booting to the correct OS (NixOS installer instead of the previously installed OS), if not try to select it manually or remove the previous OS boot entry
  • Examine the network boot process with Wireshark or Termshark

Verify your authorized SSH keys and trusted host keys if provisioning succeeds but enrollment fails.

Current decisions

Using NixOS as the base OS

Context

With Fedora and Ansible, I sometimes make manual changes and forget to put them back in the playbooks. If a playbook fails halfway, it’s also hard to roll back to the previous system.

I’ve also considered other atomic distros, for example Talos is smaller and has better integration for Kubernetes operations, but I want a general-purpose OS that can stay even if I move away from Kubernetes. I don’t want the OS to depend on a single company that could change its license, and I already use NixOS on my other machines.

Decision

Use NixOS as the base OS.

Consequences

  • System changes have to go through the NixOS configuration, so it’s easier to keep the system clean and reproducible.
  • NixOS builds the new system before switching to it, and I can roll back to a previous generation. Switching to the new system is almost fully atomic, except for service activation and restarts, which are still imperative.
  • I can use Nix for both the OS and development shells, without installing project dependencies into the base system.
  • I can test the same configurations in QEMU before applying them to real hardware.
  • I can keep the OS even if I replace Kubernetes later.
  • The system is larger than Talos, with a larger attack surface, and I need to coordinate rolling upgrades myself.

See the original discussion and NixOS cured my OCD for more background.

Switch metal provisioning from Ansible to Nixie

Context

The metal nodes used to use Ansible to install Fedora. When I switched to NixOS, I could still use Ansible to install it, but it was hard to test and debug.

Decision

Build a custom bare metal orchestration engine for NixOS - nixie.

Nixie installs from the NixOS configuration, replacing Kickstart without needing cloud-init. It works with VMs too. My staging cluster runs on Incus VMs that I regularly destroy and recreate, while production runs on bare metal. See PXE boot for the installation flow.

Consequences

  • Single binary with native OS process instead of complex Ansible & Docker Compose setup (& its host networking baggage)
  • It has much better integration to the OS, since it’s built specically for NixOS
  • It’s much more reliable and testable (Nixie has a full test suite in QEMU)
  • There’s much better visibility into the PXE boot process with tracing
  • The PXE installer can be reused with other projects (e.g., my dotfiles), not just this homelab.

K3s

K3s is reliable, well supported, and available in nixpkgs with a NixOS module. I’ve been using it for years without issues that would make me want to replace it. I replace the bundled Traefik, ServiceLB, and local storage with Istio, kube-vip, and Rook Ceph.

Replace ingress-nginx with Istio

I want a service mesh for observability, security, and traffic routing, and I need Gateway API support anyway. Istio provides both, and I’m already running it in production. Ambient mesh has the features I need without sidecar overhead.

I keep Flannel for pod networking and kube-vip for the control-plane VIP and Service load balancing. Keeping the existing CNI makes it easy to port the platform to cloud-managed Kubernetes without bringing my own CNI.

Application routes use Gateway API, and ambient mesh encrypts traffic between application Pods with strict mTLS. See Networking for the current setup.

Use Rook Ceph for storage

Ceph is reliable, battle-tested distributed storage, and Rook manages it in Kubernetes. I’ve tried Longhorn but still ran into volume detachment issues. A single NFS server would be a single point of failure, which I don’t want for cluster storage. Ceph is more complex to operate, but its reliability is worth it to me.

Use Velero for backups

Context

Requirements:

  • All apps backed up by default, without additional configuration for new apps.
  • The backups need to work even if I lose the entire cluster.

I used to use VolSync, but its Restic workflow requires per-volume replication resources and credentials, and the backup & restore flow is not really declarative. I would need additional resource generation and orchestration to provide this experience.

Decision

Use Velero to back up cluster resources and supported persistent volumes:

  • Use CSI snapshot data movement to copy volume data into object storage, so recovery does not depend on the original Ceph cluster.
  • Use Velero’s ReadOnly recovery mode to prevent backup creation and deletion while restoring and verifying data.

Consequences

  • The backup schedule includes all apps, without backup resources or storage credentials to distribute to app namespaces.
  • Backup and restore operations use Velero’s native resources and CLI.
  • Velero requires broad cluster permissions.
  • Database applications may still need backup hooks or native exports for consistent backups.

Use Kanidm for identity

I want a reliable, secure identity provider. I trust Kanidm’s maintainer and track record, and its use of Rust gives me more peace of mind.

I only use Kanidm and don’t plan to switch identity providers. Dex helped with client IDs and secrets, but added another layer and limited which Kanidm features I could use. I now integrate with Kanidm directly and automate client provisioning myself. If I switch providers later, rewriting the automation scripts is a small enough cost.

Use OpenBao for secrets

I need an API to provision application credentials automatically. For example, SSO setup can create a Kanidm client secret and write it to OpenBao for the application to use.

I could do this with the Kubernetes Secret API, but I also want secret injection and namespace-scoped access policies. Applications should only be able to read secrets under their own namespace’s path. OpenBao provides those guardrails, with Bank-Vaults handling secret injection. It’s more to maintain than the previous global secret store, but worth it for these features.

See Secrets management for the implementation.

Manage platform components through OpenTofu and ArgoCD

I already need OpenTofu for infrastructure and a way to bootstrap the platform. It gives me templating and dependency ordering, while ArgoCD deploys and reconciles the workloads. I prefer HCL to Helm templates or string replacement. User applications stay in GitOps, managed by ArgoCD.

Terragrunt gives each provisioning unit its own state and provider configuration. It handles dependencies between units without custom orchestration. The cluster must exist before I can initialize the Kubernetes and Helm providers for platform components.

OpenTofu can also provision secrets before OpenBao is available. Velero needs this because it must be able to restore OpenBao, so its credentials can’t depend on OpenBao being up first.

Use app-template for all applications

I want consistent application configuration so I can apply platform requirements like ambient mesh and future security settings in one place. All applications use app-template, with a shared ApplicationSet handling platform integration. I lose some flexibility and can’t reuse upstream Helm charts directly, but so far I’ve been able to convert every application.

App-template supports arbitrary resources through rawResources, so the chart alone isn’t a guardrail. I use separate ArgoCD projects: platform components need cluster-wide privileges, while applications have a resource allowlist. This gives me more confidence that application changes have a contained blast radius.

Use Forgejo as the GitOps source

The point of this project is to self-host, so that includes Git. I don’t want a critical platform feature to depend on a closed-source third-party service like GitHub. Forgejo lets me control the GitOps source end-to-end. If it’s down, I can still update things manually or fix it myself.

Self-hosting everything has to be practical. If it’s too complex, people won’t do it. I’m fine with managed services that provide enough value without much lock-in. DNS and S3-compatible storage are good examples: they’re commodity services, and I still own my data. Tunneling is another place where a managed service can be worth it, as long as I can replace it.

Keep Tailscale as a fallback for WireGuard

I primarily use WireGuard, but my ISP has broken access through my public IP several times. Tailscale gives me another way in when that happens. I don’t want to depend on its managed control plane as my primary access method, so I keep it as a fallback.

Remove the Docker wrapper for Nix shell

Context

The Docker wrapper was originally added because not everyone has Nix installed. However, it is not a good abstraction. Depending on how Docker (or Podman) was installed, there may be permission issues, and it is slower than running Nix directly on the host.

Decision

Remove the Docker wrapper and run the Nix development shell directly. While not everyone has Nix installed, not everyone has the same Docker setup either.

Consequences

  • Requires an additional step to install Nix, but this is a one-time setup.
  • The make tools command has been removed, you now need to run nix develop directly. Although it can be added to the Makefile, this requires make to be installed, and not everyone has the same version of make.

Replace Make with Just

Most of my commands are things I need to run, rather than things I need to build. Just fits this better, with positional arguments and support for Python recipes. Modules let me keep recipes alongside the infrastructure and tests, exposed through the root justfile. It needs an extra installation, but I already have a Nix shell that provides it.

Manage package versions in development shell

Status: I no longer need this, since I use Nix from the development shell to NixOS on the nodes.

Context

While Nix is reproducible, I need a way to control the versions of the tools and keep them up-to-date. For example, if I update the nixpkgs hash (in flake.nix) from abcd1234 to defa5678:

  • ansible: 2.12.1 -> 2.12.6
  • terraform: 1.2.0 -> 1.2.2
  • foobar: 1.8.0 -> 1.9.0

That looks good. But when I update it from defa5678 to cdef9012:

  • ansible: 2.12.6 -> 2.13.0
  • terraform: 1.2.2 -> 1.3.1
  • foobar: 1.9.0 -> 2.0.0

This time it breaks foobar because the new major version contains a breaking change.

I can pin the specific version of each dependency in flake.nix, however, the maintenance burden is too high (even with Renovate) because I need to update the version of each package regularly rather than just the nixpkgs hash. Instead, I can just bump the nixpkgs hash and run some tests to ensure there is no breaking change.

Decision

Update the tests to ensure that the versions remain within the desired range (i.e. no breaking change).

Consequences

I have the rail guard from the tests to ensure that I don’t upgrade to a new major version with breaking changes, and I can make a conscious decision to take the necessary steps prior to upgrading to the new major version.

Refactor the tools container from plain Dockerfile to Nix

Status: the Docker wrapper was later removed in Remove the Docker wrapper for Nix shell.

Context

The previous implementation of the tools container is not reproducible, if someone builds it a few weeks after me, they will receive different versions of the tools. Also, if you change something in the tool list, everything will be downloaded again, with no caching.

Decision

Move to Nix shell with a Docker wrapper, in case Nix is not available (see commit adbaf32).

Consequences

  • All versions are pinned
  • When you change the list of tools, rebuilding is much faster

Combine dhcpd and tftpd to dnsmasq in PXE server

Status: replaced by Nixie.

Context

Original proposal from @Bourne-ID:

Issue statement

The use of dhcpd is great for air-gap solutions where a new DHCP is required. However for some home networks which does not have the VLAN capability or for users who would like to use common router DHCP services, the use of DHCPD will cause duplicate DHCP servers and will result in potential network disruption, or will limit the ability to auto-provision the Metal stage of this project.

Proposed Solution: DHCP Proxy

Use DHCP Proxy services to add PXE features such as Next Server into this project. This allows for users to use the existing DHCP servers which may be locked down or incapable of using Next Server/PXE settings on their network to be able to auto-provision hardware through PXE (with certain common configurations, like static IP allocation or reduction in DHCP request ranges on the DHCP server)

Proposed Application: DNSMasq

DNSMasq in Proxy mode interoperates with existing DHCP servers over IPv4 to add features such as next-server, TFTP, etc. where such hardware is either locked or unconfigurable for such services. This would be an opt-in change, configurable through the pxe_server defaults file.

Proposed Target Audience

Users who either do not want to create their own VLAN or lack the hardware to configure such services. Users who want to use common router services for DHCP and have router access to configure static IP and/or DHCP allocation ranges.

Additional Risks with Proposed Change

  • Additional Surface Area for Break-Out Attacks: Originally this project is locked to its own DHCP/VLAN, so any break-outs should be contained accordingly. Using common home networks increases the surface area of break-out attacks if the deployment is compromised.
  • Mitigation: Enrolment into this change is opt in only.

Proposed Next Steps

  1. Trial/Adopt/Halt - A discussion with all or a decision by the project maintainers to identify if this change should exist in this project or live on a fork.
  2. Documentation (This is in flight in any situation).

Decision

Migrate to dnsmasq (see commit f650c89, thanks to @Bourne-ID)

Consequences

  • DHCP proxy is enabled by default because most people have a standard home network with existing DHCP server, but it can still be disabled to restore the previous behavior

Contributing

How to contribute

Bug report

You can create a new GitHub issue with the bug report template.

Submitting patches

Because you may have a lot of changes in your fork, you can’t create a pull request directly from your master branch. Instead, create a branch from the upstream repository and commit your changes there:

git remote add upstream https://github.com/khuedoan/homelab
git fetch upstream
git checkout upstream/master
git checkout -b contrib-fix-something

# Make your changes here
#
# nvim docs/README.md
# git cherry-pick a1b2c3
#
# commit, push, etc. as usual

Then you can send the patch using GitHub pull request or git send-email to mail@khuedoan.com.

FAQ

Is it necessary to install Linux on my servers before setting up the homelab?

No, and that’s the beauty of this setup. You start with empty hard drives, type a single command on your laptop/PC, and it will install the operating system for you automatically and in parallel over the network.

Is it necessary to keep the PXE server running?

No, the ephemeral PXE server is stateless, once Linux is installed on your servers, you can shut it down (or not, ideally, you don’t even need to be aware of its existence). The Terragrunt metal module runs Nixie when you apply it.
